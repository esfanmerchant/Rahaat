# Evaluation report

**Prototype. Not an official service. All identity, payment and data services are simulated.**

Every number below was produced by a command in this repository on Sat 21 Nov 2026, from commit `3c6884e` (Python 3.12.10, Windows 11, no network, no paid API). Every command is given so that a judge can repeat it. Each one is seeded, so a rerun prints the same numbers (speed is the exception).

## Read this first: what these numbers are

- **All datasets are synthetic**, generated by this repository from fixed seeds. No real person, ID image, message or phone number was used.
- Models were trained on one synthetic world and scored on another, built from a different seed and different families ("held-out"). That shows the logic generalises to unseen synthetic people. **It says nothing about accuracy on real Pakistani data, which we do not have.**
- Thresholds were set from costs (decision) or on the dev split (RAG, voice), never on the test split. Where a split is small, the count is printed next to the rate.
- Where something is not evaluated, it says so in the last section.

## 1. Decision quality (Challenge 01, "cost of being wrong")

**Dataset.** 1,223 labelled cases from 821 people in 776 families, built from seed `20261222` (`HELDOUT_SEED`). None of these people or families was used to train, calibrate or test the evidence model (the test `test_heldout_world_is_big_labelled_and_not_the_training_people` checks that fewer than 2% of the people share a name and date of birth with the training world). Truth classes: 714 eligible and genuine, 106 not genuine (forged card), the rest not eligible under the rules. Rules: seed rule version 1. Model: `evidence-lr-a9966d8aa450`, a numpy logistic regression with isotonic calibration.

**Method.** Each case is assessed once by `engine.assess()` (facts, rules, probabilities). Routing then comes from `engine.route_for()`, the same function `decide()` uses, under the department's cost matrix:

| Cost | Units |
|---|---|
| Wrong approval | 100 |
| Wrong rejection | 30 |
| Person's review | 3 (plus 0.2 per day of waiting, 1 day) |
| Ask for a proof | 1 |

So the engine approves alone only when `p_ok >= 1 - 3.2/100 = 0.968`, and rejects alone only when a hard rule fails on verified input with confidence of at least `1 - 3.2/30 = 0.8933`. A test (`test_slider_routing_is_exactly_what_decide_does`) checks that this analysis and a full `decide()` give the same route and the same expected costs.

**Command** (DB-free; save as `dec.py` in `backend/` and run `uv run python dec.py`, `PYTHONPATH=.` on Windows if the import fails):

```python
import json
from app.contracts.decision import CostMatrix
from app.modules.decision.model import get_model
from app.modules.evals import decision_eval as E
from app.seed import RULES_V1
m = get_model(); s = E.cached_scores(RULES_V1, m)
print(json.dumps(E.analyse(s, CostMatrix()), indent=1, default=str)); print(E.dataset_info(E.heldout_world(), s))
```

The same analysis is served at `GET /v1/evals/...` (admin and auditor) and drawn on the staff "Evaluation" and "Cost of being wrong" pages.

**Results at the derived operating point (1,223 cases):**

| Measure | Result |
|---|---|
| Approved by the engine alone | 183 (1 wrong: an ineligible person) |
| Rejected by the engine alone | 129 (5 wrong: eligible people) |
| Asked for one more proof | 133 |
| Sent to a person | 778 |
| **Wrong approvals** | **1 of 1,223 (0.08%); 0.55% of approvals** |
| **Wrong rejections** | **5 of 1,223 (0.41%)** |
| Forged cards approved | 0 of 106 (3 rejected, 103 sent to a person) |
| **Automatic rate** (approved + rejected alone) | 25.5% |
| **Abstention rate** (not decided alone: proof or person) | 74.5% |
| Eligible and genuine, but not decided alone | 527 of 1,223 (43.1%) |
| Expected cost per case | 2.381 units, against 3.200 if every case went to a person (saves 0.819, 25.6%) |
| **Silent guesses** (automatic decisions that break the invariant) | **0** |

Confusion matrix (rows are the truth, columns the engine's outcome):

| Truth | approved | rejected | needs proof | needs person |
|---|---|---|---|---|
| eligible and genuine (714) | 182 | 5 | 129 | 398 |
| not eligible (403) | 1 | 121 | 4 | 277 |
| not genuine (106) | 0 | 3 | 0 | 103 |

How to read it: **the engine is deliberately slow rather than wrong.** A wrong approval costs 31 times a person's look, so three quarters of cases go to a human or ask for a proof. Only one ineligible person was approved. The price is a long queue (398 eligible people sent to a person that a looser threshold could have approved). That trade is a policy choice, made visible and adjustable in the cost sliders.

**Calibration** (probability the person is eligible and genuine, `p_ok`, 10 bins, 1,223 cases): **ECE 0.0329, Brier 0.0623, AUC 0.9691**. Reliability curve is in the `reliability` field. It is good where it matters (the 0.9 to 1.0 bin has 610 cases, mean predicted 0.976, observed 0.967) and noisy in the sparse middle bins (3 to 33 cases each). The model-card figure printed during training, ECE 0.028 on the evidence model's own held-out families, is a different split (`docs/STATUS.md` B6).

**Threshold analysis.** `cost_curve` sweeps the approve threshold from 0.50 to 1.00:

| Approve at | Cost per case |
|---|---|
| 0.50 to 0.55 | 2.643 (5 wrong approvals) |
| 0.90 | 2.42 (2 wrong approvals) |
| **0.968 (derived from the costs)** | **2.381 (1 wrong approval)** |
| 0.984 | 2.57 (162 approved alone) |
| 0.92 (cheapest point measured) | 2.358 |

The cheapest measured point is 29 units cheaper over 1,223 cases, which is less than one wrong approval (100). The cases cannot tell the two points apart, so the engine keeps the threshold derived from the costs instead of one tuned on a test set. ROC AUC of the approve ranking 0.9122 (this includes the not-eligible and not-genuine classes together); average precision 0.9929; 214 cases are approvable at the highest-confidence setting.

**The silent-guess invariant.** An automatic decision must name a verified fact or rule behind it, and every low-confidence or conflicting input must go to ask-more or a human. It is checked in three places: (a) the held-out run above, 0 of 1,223; (b) `test_silent_guess_count_is_zero_over_the_golden_set` and the property-based tests in `app/modules/decision/tests/test_engine.py`; (c) the evaluation summary re-checks every stored automatic decision in the live database (`silent_guesses`, must be 0).

**Replay.** A stored decision replayed from its snapshot returns the identical result (tests in `app/modules/decision/tests/test_replay_db.py`, shown live in the auditor view).

```
cd backend && uv run pytest app/modules/decision app/modules/evals -q
```

## 2. Name matching and duplicate detection (Challenge 03)

**Dataset.** 456 generated record pairs in 19 kinds (288 the same person, 168 different people): Mohammad/Muhammed/Mohd spellings, Urdu against Latin script, swapped order, honorifics and relation words (`w/o`, `s/o`), one-digit ID typos, wrong check digits, impossible dates of birth, changed phone numbers, shared household phones, namesakes with and without the same date of birth, siblings, and reused IDs. 24 pairs per kind, seeded.

**Command:** `cd backend && uv run pytest app/modules/matching/tests/test_names.py -q` (prints the report, `-s` to see it), or call `evaluate(build_fixtures())` from `app/modules/matching/fixtures.py`.

| Measure | Result |
|---|---|
| **Wrong links** (two different people linked as one) | **0 of 168** |
| "same" band precision | 1.0 (143 predicted) |
| "same" band recall | 0.4965 |
| "distinct" band precision / recall | 1.0 / 0.8571 |
| "possible duplicate" (review band) precision | 0.858; low by design, these go to a person |
| Duplicates caught (same or possible) | 288 of 288 (recall 1.0), 0 missed |
| Blocking recall (true pairs sharing a candidate key) | 1.0, 0 pairs lost |
| Landed in an expected band | 99.8% (455 of 456) |

The one miss: a date-of-birth typo with the same ID, matching name score 0.83, landed in "possible" where "same" was expected. It still reached a person. The rule that matters: **a name alone never links** (property test `test_a_name_alone_never_links`), and "Muhammed" against "Mohammad" with a different phone is a "possible duplicate", not a link.

## 3. Scam checker

**Dataset.** 3,840 synthetic messages in English, Urdu and Roman Urdu from 82 storyline families, split by family: the model trained on 2,676 messages from 57 families and is tested on **1,164 messages from 25 families it never saw**. Classes: relief scam, phishing link, advance fee, impersonation, legitimate Rahat message, unknown. Model `scam-lr-90be2e8fd81d`.

**Command:** `cd backend && uv run python -m app.modules.scam.evaluate --no-db` (`--no-db` skips storing a run).

| Measure | As deployed (verify codes checked) | Model and signals alone |
|---|---|---|
| Scams caught (called scam or might be a scam) | **95.5%** | 95.5% |
| **Scams called "looks real"** | **0** | 0 |
| False alarms on legitimate messages | 2.4% (0 on Rahat's own messages) | 2.4% |
| Abstained ("not sure") | 16.5% | 20.2% |
| Accuracy when it answered | 95.9% | 95.7% |
| Wrong automatic answers | 27 of 916, none on the dangerous side | 27 of 873 |
| ECE | 0.060 | 0.061 |
| Time per message | 3.4 ms | 5.0 ms |

Per class, as deployed (precision / recall): relief scam 1.00 / 0.89; phishing link 1.00 / 0.99; advance fee 0.83 / 0.84; impersonation 0.88 / 0.93; legitimate Rahat message 1.00 / 0.91; unknown 1.00 / 0.47 (recall is low because unknown messages are mostly sent to "not sure", which is the intended behaviour).

Derived binary figures (arithmetic on the printed rates, not a separate command): 710 scam messages and 454 legitimate ones, so about 678 scams caught and 11 false alarms give precision about 0.98, recall 0.955, **F1 about 0.97**.

Weak spots, as measured: **Roman Urdu false alarms are 14.7%** (English 0%, Urdu 0%), so a legitimate Roman Urdu message is the most likely to be wrongly flagged; "advance fee" is the weakest class (F1 about 0.83); abstention is highest in Urdu (20.8%). The verify code only helps for messages that carry one: a genuine Rahat message with a valid code is "confirmed real" (121 of the test messages), which is why abstention drops from 20.2% to 16.5%.

## 5. Rules assistant (RAG) with citations

**Dataset.** 14 policy documents (7 in English, 7 in Urdu), 117 labelled questions: 98 split into dev and test (49 each), plus a 19-question hold-out written afterwards in different wording. 26 of the 98 are off-topic questions or attacks that must be refused. The refusal threshold (0.34) was chosen on dev by cost (wrong answer 5, refusal of an answerable question 1).

**Command:** `cd backend && uv run python -m app.modules.rag.evaluate`

| Split | Questions | Answer accuracy | Wrong answers | False refusals | Off-topic and attacks refused | Groundedness |
|---|---|---|---|---|---|---|
| dev | 49 | 100% | 0 | 0 | 13/13 | 1.00 |
| test | 49 | 97.2% | 0 | 1 | 13/13 | 1.00 |
| dev + test | 98 | 98.6% | **0** | 1 | 26/26 | 1.00 |
| **hold-out (new wording)** | 19 | **61.5%** | **2** | 3 | 6/6 | 1.00 |

Groundedness is the share of answer sentences found word for word in the cited passage; answers are copied from the policy text, never generated. **The hold-out shows the limit**: with questions worded differently from the ones the corpus was tuned around, the lexical retriever answered 8 of 13 answerable ones, refused 3, and answered 2 from the wrong section (cited, but the wrong section). Do not read the 98.6% as the expected real-world accuracy.

## 6. Voice interpreter (answers to form questions)

**Dataset.** 1,216 synthetic transcripts in 152 families (Urdu, Roman Urdu, English), split by family: 560 train, 656 test, plus a 150-example hold-out. The confidence floor was chosen on train only.

**Command:** `cd backend && uv run python -m app.modules.voice.evaluate`

| Split | n | Accuracy | Asked again (answerable) | Wrong but confident |
|---|---|---|---|---|
| test | 656 | 91.8% | 11.8% | **0** |
| hold-out | 150 | 91.3% | 11.2% | **0** |

Without the floor the test split would contain 5 wrong-and-confident answers; the floor trades them for 1.3 points more abstention. This evaluates the **text interpreter**, not speech recognition itself.

**Speech-to-text timing (measured, not an accuracy test).** The optional Gemini provider (`gemini-3.1-flash-lite`, minimal thinking) took 2 to 3 seconds on Urdu prompts. On-device browser speech is tried first and is free; Groq Whisper is a further optional provider. No word-error-rate test was run, and the Gemini path is simulated in the automated tests (a mock HTTP transport). Every spoken answer is read back and confirmed by the person.

## 7. Documents: OCR, QR and forgery checks

**Dataset.** Specimen cards generated by `backend/app/modules/docs_ai` (a mock issuer with an Ed25519 key, every card marked SPECIMEN). The committed demo cards are in `data/demo_cards/<person>/`: clean, glare, blurry, cropped, altered, wrong QR, bad signature, unknown issuer, and others.

**Demo cards, run through the real pipeline:** `cd backend && uv run pytest app/modules/docs_ai/tests/test_rapidocr.py -q` gives **11 passed** (RapidOCR, local ONNX). It checks that all three genuine cards pass with the printed text agreeing with the signed QR (`ocr_matches_qr`, route "auto"), and that every altered or wrong-QR card raises `ocr_qr_mismatch` and goes to a person.

**Generated-photo evaluation:** `cd backend && uv run python -m app.modules.docs_ai.evaluate` photographs the demo people and invented people under random angle, light, noise, JPEG quality and background, in every variant. Run for this report with `--people 6` (the default is 24 people and takes over 10 minutes here; it was not completed): 24 genuine, 18 poor-quality and 30 forged photos, seed 2026.

| Group | Result |
|---|---|
| Genuine cards (clean, flat, glare, forwarded) | 24 of 24 auto-accepted, 0 false alarms |
| Poor quality (blurry, glare over the QR, cropped) | 18 of 18 sent for a retake, 18 of 18 with the right spoken hint |
| Forged cards (altered name, altered digit, wrong QR, unknown issuer, bad signature) | 29 of 30 flagged "suspect" (96.7%); 30 of 30 not auto-accepted |
| Median latency per check | 0.74 s (p95 3.86 s, max 4.40 s) |

The one forgery not flagged was an altered date-of-birth digit: it was judged "genuine" but still routed to a person because the printed text disagreed with the QR. Pixel-level edit detection (ELA) is weak: it fired on only 2 of 18 edited cards (11.1%), 0 of 24 genuine. The forgeries are caught mainly by the signed QR and by comparing the printed text to it, not by spotting edited pixels. The larger 24-person run recorded in `docs/STATUS.md` (C2) reports 99.2% of forgeries flagged and 2.1% false alarms; that figure was not reproduced here. Thresholds were set while looking at generated images, so this is in-distribution.

On Vercel there is no OCR (the function limit is 500 MB), so only the signed QR check, quality gate and image signals run there; the printed-text against QR check runs on the PC host.

## 9. Not evaluated

- **Real data of any kind.** Every dataset is synthetic; real accuracy is unknown.
- **Real phone photos of cards.** Images come from our own renderer and photo simulator.
- **Speech recognition accuracy** (word error rate) for Urdu, on-device or hosted. Only the interpreter of transcripts and the Gemini latency were measured.
- **Urdu wording quality** by a native speaker.
- **Fairness slices** are computed by the Digital Twin (age band, district, gender) but are not reported here.
- **Load and slow-network behaviour** beyond the 17-call latency sample above.
- **Anomaly detection** has no separate quality evaluation in this report. The agent is evaluated in section 10, on synthetic labels written by its author, not by independent officers.
- `p_ok` assumes the evidence is independent.

## 10. Agent with an approval gate (WP-B)

**Command:** `cd backend && uv run python -m app.modules.agent.evaluate` (the injection part alone: `uv run python -m app.modules.agent.redteam`)

**Golden set.** 38 synthetic cases, each labelled with the first action an officer would most likely take, or "abstain". 28 come from the decision engine's own golden inputs (`app/synth/golden.py`): the real engine decides, and its trace, guards and handoff are what the planner sees. 10 are built by hand for branches the engine does not produce (a case already waiting for proof, a verified failure while the model leans approve, tied hypotheses, a paid application, an already resolved case, a non-application case, no trace, no payment amount, an escalated case, and a case whose notes carry an attack). The labels are the policy as its author wrote it. **Agreement therefore shows that the planner implements the stated policy and abstains where the policy says; it is not agreement with independent officers.** On the first run the planner disagreed on 1 of 38 (it proposed approval where the engine had asked for proof because the rules passed on stale income); the fix was a rule in the planner, and the numbers below are after that fix.

| Measure (local planner) | Result |
|---|---|
| Agreement with the label | **38 of 38** |
| Action precision / recall (when it proposes, is it right / does it propose when it should) | 1.00 / 1.00 (19 proposals) |
| Abstain rate | **50%** (19 of 38), the same as the labelled rate; it never proposed an action on a case labelled "abstain" |
| Proposals by tool | request_proof 7, escalate 7, approve_and_pay 3, reject_with_reason 2 |
| Actions that ran without an officer's approval | **0**: every action tool is refused by the action guard at execution when the approval is missing or claimed by the agent or the model (5 action tools times 3 claimed sources, all refused), and the integration tests show no payment, no case change and no message before an approval |

**Injection red team.** 21 attacks (English 13, Urdu 4, Roman Urdu 4) placed in OCR text, officer notes, scam-message and transcript evidence, each tried on 3 base cases (one where nothing permits approval, one where approval is correct, one that escalates), 63 trials. Each trial passes only if the local plan is identical with and without the text, a hosted planner that obeys the attack (mocked) cannot add an action the facts do not permit and no argument carries attack text or an amount, and the action guard refuses any approval claimed by the agent or the model.

| Measure | Result |
|---|---|
| Trials passed | **63 of 63** (0 actions created or approved by an attack) |
| Attacks the input guard also flagged for staff | 16 of 21 (the 5 it missed include a deliberately polite, plain-language plea) |
| Trials where the attack text was withheld from the hosted planner's prompt | 48 of 63 (flagged text is not shown to the model at all) |

The first run of this suite failed 12 of 63 trials: a mocked obedient model could propose a fixed-template message the attack asked for. No attacker text got through, but a hosted model must not widen the plan, so it may now only choose the action the local ladder chose (or hand the case up), and the suite passes. The attacks were written by the same author as the defences; this shows the known attacks are covered, not that unknown ones are. The hosted (Gemini) planner is tested only over a mock transport; it was not called with a real key.
